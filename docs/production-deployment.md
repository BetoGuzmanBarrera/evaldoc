# Preparación de producción (sin despliegue)

Este documento es un runbook para una ejecución futura aprobada. **No se ha creado, enlazado ni modificado un Supabase remoto**, dominio, DNS o hosting. Un responsable debe revisar costos, retención de datos, privacidad y credenciales antes de operar con información real.

1. Crear un proyecto Supabase exclusivo para EvalDoc y registrar región, versión PostgreSQL compatible y responsables. Guardar las claves en un gestor de secretos. La clave `service_role`, contraseña DB, JWT secret y secret Turnstile jamás van al repositorio, `VITE_*` ni bundle.
2. Revisar las ocho migraciones en orden y el seed. El seed contiene **siete instituciones de muestra**, cinco roles y plantilla oficial de 15 reactivos; **no** contiene campus, programas, docentes, alumnos ni facilities reales. Para un despliegue institucional real, decidir qué instituciones del seed son pertinentes y preparar carga autorizada de estructura académica. No aplicar automáticamente un `db reset` en producción: borraría datos.
3. Con acceso aprobado, ejecutar las migraciones mediante el proceso controlado de Supabase CLI/CI para el proyecto correcto, revisando el plan y respaldo antes de cada cambio. Comprobar 18 tablas, RLS en todas, 17 políticas, grants mínimos, triggers, FK y funciones. No usar `supabase link`/`db push` sin autorización separada.
4. Configurar Auth: `Site URL` del dominio HTTPS, allowlist exacta de `/login`, `/email-confirmation` y `/reset-password`; confirmación de correo activada; política de contraseña de al menos ocho caracteres con mayúscula, minúscula, dígito y símbolo. Verificar plantillas, SMTP transaccional, remitente, entrega, caducidad de enlaces y límites de frecuencia. Revisar redirecciones desde subdominios y evitar comodines amplios.
5. Crear widget **real** Cloudflare Turnstile limitado a los dominios de EvalDoc. Configurar la site key pública como `VITE_TURNSTILE_SITE_KEY` en el build y la secret exclusivamente en Supabase Auth, donde se valida el token. Las claves de prueba locales nunca protegen producción. Probar registro, login, recuperación, token ausente/erróneo, expiración y falla de red en staging.
6. Publicar frontend desde `npm ci && npm run lint && npm run build`. Configurar únicamente `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (clave pública) y `VITE_TURNSTILE_SITE_KEY` (pública), correspondientes al mismo proyecto. Recompilar cuando cambien. Servir `dist/` por HTTPS; configurar fallback SPA a `index.html` para rutas como `/teacher/history` y `/reset-password`, manteniendo assets estáticos. No subir `.env` ni `.env.local`.
7. Crear usuarios de prueba **solo en staging**, verificar confirmación, pending, activación administrativa, aislamiento entre instituciones, umbral de cinco, PDF y redirecciones. Ejecutar suites SQL en base desechable, no con fixtures en producción. Comprobar que los roles privilegiados solo se asignan por proceso administrativo seguro, nunca por metadata de registro.
8. Antes del corte, revisar respaldo/restauración, monitoreo de errores sin tokens/PII, retención de respuestas, avisos de privacidad, política de acceso de personal y respuesta a incidentes. Tras publicar, validar health de Auth, rutas SPA, correo, captcha, RPC y RLS desde cuentas de cada rol; documentar la evidencia operativa.

La UI actual no ofrece alta administrativa de campus, programas, matrículas o instalaciones. Ese aprovisionamiento debe diseñarse y autorizarse antes de operar una institución real; la existencia del esquema no lo suple. La generación PDF es local al navegador y la inferencia por diferencias temporales en agregados pequeños sigue siendo un límite de privacidad. Referencias: [RLS de Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security), [Auth CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha), [Turnstile](https://developers.cloudflare.com/turnstile/get-started/).
