# Auth, perfiles y roles

El cliente React usa `@supabase/supabase-js` con `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY`. `.env.local` está ignorado por Git. Nunca se entrega una clave `service_role` al navegador. El login usa `signInWithPassword`; el logout usa `signOut()`. `AuthProvider` restaura la sesión, se suscribe una sola vez a cambios de Auth y lee perfil, institución y roles desde PostgreSQL. El cliente usa los roles para navegación; RLS y las RPC aplican la autorización de datos.

El registro público crea `auth.users` y el trigger `app_private.handle_new_evaldoc_user()` crea `profiles.id = auth.users.id` con estado `pending` y **solo** el rol `student` tomado de la tabla `roles`. El trigger valida institución y datos de perfil e ignora `role`/`roles` de metadata editable. La función está en un esquema no expuesto y su ejecución directa está revocada. La FK del perfil a Auth usa `ON DELETE CASCADE`; otras referencias académicas pueden impedir el borrado de una cuenta con actividad histórica.

En el proyecto local, la contraseña requiere al menos ocho caracteres, mayúscula, minúscula, dígito y símbolo. Registro y reset muestran los cinco requisitos mientras se escribe y comprueban la confirmación antes de enviar. Supabase Auth aplica la misma política en el servidor. Los campos de contraseña usan estado transitorio de React y control accesible mostrar/ocultar; no se guardan en almacenamiento persistente ni en URL.

`supabase/config.toml` exige confirmación de correo. Tras `signUp`, una respuesta sin sesión lleva a `/email-confirmation` con el mensaje de revisar Mailpit. El enlace de Auth devuelve una sesión confirmada a esa ruta; la pantalla comprueba el usuario con `getUser()`. Confirmar el email **no** cambia `profiles.status`: el perfil sigue `pending` hasta una validación institucional separada. Un perfil `pending` puede iniciar sesión, consultar su identidad propia y cerrar sesión; no recibe catálogo académico ni puede enviar evaluaciones. Las rutas académicas lo dirigen a `/pending`.

`/forgot-password` llama `resetPasswordForEmail()` y muestra la misma respuesta neutral para cuentas existentes e inexistentes. `/reset-password` solo presenta el formulario cuando `AuthProvider` ha recibido `PASSWORD_RECOVERY` o comprobado que el fragmento de recuperación inicial coincide con el token de la sesión restaurada, y `getUser()` valida al usuario. Esta comprobación cubre el caso en que Auth consume el enlace antes de que React se suscriba al evento. Aplica la política de contraseña, llama `updateUser()`, cierra la sesión y redirige al login tras el cambio. Un acceso directo, una sesión normal o un enlace inválido muestra la opción de solicitar otro enlace.

El login distingue credenciales incorrectas, email sin confirmar, perfil `pending`, cuenta activa y fallo de servicio con mensajes controlados. La prioridad visual de inicio multirrol es admin → hr → coordinator → teacher → student. Esta prioridad no reemplaza RLS. Los roles privilegiados no se pueden reclamar durante el registro público.

La afiliación institucional todavía no se comprueba por dominio de correo ni por un padrón externo: institución e identificador se validan sintácticamente y luego quedan pendientes de validación institucional. Los dashboards y evaluaciones reales se describen en [Autorización RLS multiinstitución](rls-authorization.md) y [Flujo de evaluación del alumno](student-evaluation-flow.md). Para configuración local, pruebas, redirects y límites de este bloque, véase [Seguridad de cuenta](account-security.md).
