# Auth, perfiles y roles

El cliente React utiliza un único `@supabase/supabase-js` configurado con `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY`. Copia `.env.example` a `.env.local` y completa los valores del proyecto local; `.env.local` está ignorado por Git. Nunca uses una clave `service_role` en Vite.

El registro público envía email, contraseña, nombre, identificador institucional e institución activa a Supabase Auth. El trigger `app_private.handle_new_evaldoc_user()` valida los tres datos de perfil, crea `profiles.id = auth.users.id` con estado `pending` y asigna **únicamente** el rol `student` desde la tabla `roles`. Ignora por completo cualquier campo `role` o `roles` de metadata editable por el cliente. La función está en un esquema no expuesto y su ejecución directa está revocada. La FK a Auth usa `ON DELETE CASCADE`; los roles se borran con el perfil, mientras las referencias académicas históricas pueden impedir el borrado de cuentas con actividad.

La institución y el identificador vienen del cliente y se validan sintácticamente, pero no prueban afiliación real. El correo tampoco se coteja con dominios institucionales. Pending no equivale a verificación institucional: el Bloque 6 bloquea su acceso académico mediante RLS y lo dirige a /pending. La validación institucional y la activación segura quedan pendientes. No hay interfaz pública para otorgar roles privilegiados ni políticas de escritura cliente sobre las tablas de roles.

El AuthProvider escucha los cambios de sesión, restaura la sesión persistida y lee perfil, institución y roles desde tablas con RLS propia. El cliente usa estos roles solo para navegación. La prioridad de inicio para cuentas con varios roles es admin → hr → coordinator → teacher → student; una ruta de otro rol redirige al inicio permitido. Un usuario con varios roles puede abrir directamente las rutas de cualquiera de sus roles. Las cuentas pending se dirigen a /pending y pueden cerrar sesión. La seguridad real de los datos académicos la aplican las políticas RLS del Bloque 6, no el router.

El login admite email y contraseña mediante `signInWithPassword`; el identificador institucional no se usa como credencial porque Auth no lo admite directamente. El logout llama `supabase.auth.signOut()`. En `supabase/config.toml` local, `enable_confirmations = false`, por lo que el registro devuelve una sesión inmediata. La UI también maneja `session = null` y pide confirmar correo si esa configuración cambia. El URL y los redirects locales configurados apuntan a Vite en 5173; si Vite usa otro puerto temporal, habrá que añadirlo a la lista antes de probar confirmación por email.

Los dashboards y las evaluaciones académicas siguen usando mocks. El Bloque 6 añade autorización de lectura multiinstitución y bloqueo de pending en la base, sin abrir escrituras académicas. El PR #7 debe implementar el flujo seguro de evaluaciones y resultados docentes agregados sin exponer student_id; la validación de afiliación, activación y asignación administrativa de roles también siguen pendientes. Véase [Autorización RLS multiinstitución](rls-authorization.md).
